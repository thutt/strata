INSTALL POLICY (WORKLIST W61)
=============================

The owner's rule: "If the user running the installer is root, query for
permission and install everything if allowed.  If running as non-root, install
in the user's home directory, if the minimum set of prerequisites are
available.  If the prerequisites are not all available, do not install."

The script is scripts/strata-install; run it directly, with --build-dir for a
build.  ('strata-build install' makes the install tarball and installs
nothing; strata-build is a tool of the developers and is never shipped.)  The
tests are tests/installtest.py (prereq_question_test for an administrator,
prereq_default_test, user_prereq_test for anybody else).  No test installs a
package or uses sudo: a directory of small programs first in the PATH plays
apt-get, apt-cache and id.

The cases
---------

1. An administrator (id -u is 0, no --destdir).
   - The default prefix is /usr.
   - The script prints what is present and what is missing, then a table of
     the packages that apt would install with the estimated sizes, then asks

         Install these packages? [y/N]

   - Only y or Y installs.  Any other answer, or an empty one, installs
     nothing and the status is 3.  --yes answers yes.  Without a terminal and
     without --yes nothing is installed and the status is 4.
   - The packages go in with apt-get install.  The offer to run apt-get
     update after a failure with the symptom of an old index is unchanged.
   - When nothing is missing, Strata is installed with no question.

2. Anybody else (no --destdir).
   - The default prefix is ${HOME}/usr.  Without a HOME the option
     --prefix is required.
   - The programs that Strata can use at run time are OPTIONAL prerequisites
     (LaTeX with the files of the Printer, dvipng, pdftoppm of poppler-utils,
     ghostscript, aspell or
     hunspell, the thesaurus data, a print queue, curl and unzip).  Only the
     terminal or X server and the font are required, and the script cannot
     check those.
   - A missing optional program never stops the install: Strata is
     installed, and the exit status is 0.  This holds for a shared library
     too (decision of 2026-11-26, after the clean-machine trial of 1.0.0):
     the libraries libxft2 and libfontconfig1 that the window version
     needs were required items, and the install of an ordinary user stopped
     with "4 required item(s) missing", although a user without root cannot
     install a library and the terminal version needs none (str, stred and
     strprint link only the C library).  A missing library is an optional
     item of the block, with the programs that will not start until its
     package is installed (str-x11 and stred-x11; dviview for the libraries
     of the Viewer), and the closing sentence of the block says that only
     the programs named as not starting are lost.
   - The check of the TeX files that a print needs is the check of
     scripts/check-tools: adjustbox.sty, needspace.sty, extarticle.cls,
     pmboxdraw.sty (texlive-latex-extra), tikz.sty (texlive-pictures),
     ulem.sty (texlive-plain-generic), xcolor.sty, setspace.sty,
     pdflscape.sty (texlive-latex-recommended), fancyhdr.sty
     (texlive-latex-base), ptmr8t.tfm, phvb8t.tfm, pplr8t.tfm
     (texlive-fonts-recommended), tgtermes.sty (tex-gyre) and lmodern.sty
     (lmodern).  The clean-machine trial found that a print failed with
     only the first five packages of the old list.
   - The pictures that the installed manuals name are installed in
     share/strata/doc/pictures, next to the documents, so that a print or a
     preview of an installed manual has no picture error.  The list shown at
     the end of the install gives the count and the folder, and not the
     names of the 200 files.
   - Nothing about the missing programs is printed in the middle of the run,
     where it could scroll off the screen.  The check records them.
   - The warning is the LAST block of the output, after the list of what
     was installed.  Its first line is "Optional programs are missing:".  It
     lists each missing package with what is lost without it, a sentence that
     Strata runs without them, and the command for an administrator on one
     line (sudo apt-get install --no-install-recommends PACKAGES), or the
     advice to use the package manager of the system when there is no
     apt-get.  The block is printed on the error output, also with --quiet.
   - When nothing is missing no block is printed.  --dry-run writes nothing;
     --list-prereqs only reports at once and the status is 0.
   - A prefix on the command line (--prefix DIR) follows the same rules.
   - For an administrator who declines the question the same block ends the
     output (the status is 3 and nothing is installed).

3. --no-prereqs installs Strata alone, with no check and no warning, for
   everybody.  It is the user's own request.

4. --destdir (building a package) keeps its meaning: no prerequisites are
   looked for, the files go under DESTDIR/PREFIX, and the home directory is
   not used as a default.

What was removed
----------------

An ordinary user's install used to download the missing packages with
apt-get download, unpack them with dpkg-deb into lib/strata/prereq below the
prefix, write share/strata/prereq-env.sh, prepare the TeX files in that tree
and ask "Download N packages into PREFIX?".  All of that is gone, with the
private apt state (the variable STRATA_APT_STATUS) and the test that fetched
125 packages from a network (STRATA_TEST_PREREQS).

Kept for installs that an older script made: strata-run still reads
share/strata/prereq-env.sh when it exists, the check still looks in the old
tree, and the uninstall still removes a manifest entry of a tree.


The release directory (the install without the build tree)
----------------------------------------------------------

A user never has the build script or the source.  What is delivered is a
release directory with two entries:

  strata-install     the install script, a copy of scripts/strata-install
  payload/           the files to install, with the layout of an installed
                     prefix: bin/ (str, stred, strprint, dviview and the
                     X11 versions), share/strata/ (the help file, VERSION,
                     the documents and their PDF files, the templates, the
                     samples and the Tutorial) and share/doc/strata/

A developer makes it from a build with 'strata-build release DIR' (the
option --make-release DIR of the script).  The payload has no manifest and
no launcher: the script makes them.

The script uses the directory payload next to itself when no --payload and
no --build-dir is given, and --payload DIR names another one.  An install
from a payload, like every install, writes only below the prefix (below
${HOME}/usr for an ordinary user); the uninstall (--uninstall) reads the
manifest and removes what the install put there and nothing else, so the
user needs no other tool.  --list-prereqs and --check need no payload.

The specification of the file formats (strata-file-format) is a document for
developers.  It is never delivered: an install from the build directory
leaves its document and its PDF out, and a payload that holds it is refused
before anything is installed.  The test tests/installuser.py checks all of
this as an ordinary user, with a private home directory, from a release
directory with no source.


The install tarball
-------------------

The install tarball is a build artifact.  The build makes it into the build
directory, never into the source tree, and it is never committed.

How it is made.  It is made only on request: 'strata-build install-tarball'
makes it for the current build type, after the programs are built (the
target all builds everything that the payload needs).  The default build,
with no argument, and every other target leave no tarball, and 'strata-build
tarball' is not a target (owner decision, 2026-11-24).  'strata-build help'
lists the target.  The script is scripts/strata-install-tarball:

  1. The release directory is made in BUILD_DIR/image/strata-NAME with the
     install script and the payload that 'strata-build release DIR' makes,
     and INSTALL.txt, made from the template scripts/INSTALL-USER.txt.
  2. The tarball BUILD_DIR/strata-NAME.tar.xz holds that directory as its
     only top-level entry.
  3. The file BUILD_DIR/strata-NAME.tar.xz.sha256 holds the checksum, written
     from inside the build directory so that the file name is relative; the
     user checks the download with 'sha256sum -c'.

NAME is the version of the build (the first line of the file version in the
build directory) in which every run of characters other than letters, digits,
dot, underscore and hyphen is one hyphen: the version "development-1
230cb783" gives strata-development-1-230cb783.  The build type is part of
the name only when it is not release: a debug build makes
strata-development-1-230cb783-debug.tar.xz, which is for tests only.  A
build whose version is UNSUPPORTED BUILD CONFIGURATION makes no tarball; the
build prints one line that says so and is no failure.

The manuals are required.  It is a fatal error to make the tarball without
the manuals and the PDF files of the manuals (owner decision, 2026-11-24).
The manuals are the documents GettingStarted, cheat, cheat-short, mathcheat,
errata, strata-reference-manual and terminal-keys of manual/doc in the source
tree (committed files), and the document challenge ("How do your document
preparation systems fare?"; manual/challenge/challenge.doc, installed in the
folder doc/challenge with its pictures below it, owner decision 2026-11-25),
and the PDF files of all of them but terminal-keys (a part of the Reference
Manual with none of its own) in manual/pdf of the build directory.  The
specification of the file formats is never delivered.
The one list is in scripts/strata-install (strata-install --list-manuals
prints it); the tarball script and the tests use it, so that they cannot
differ, and tests/installtarball.py proves that it is the set of the
documents that the install delivers.  The checks are three, made in
different places so that none hides the failure of another:

  1. Before anything is made, scripts/strata-install-tarball asks the install
     script to check the manuals (strata-install --check-manuals): every
     document must exist and not be empty, and every PDF file must exist, not
     be empty, and begin with the bytes %PDF.
  2. The release directory is made with the option --require-manuals of the
     install script, which makes the same check and stops before it copies a
     file; 'strata-install --make-release DIR' always passes it.
  3. After the tarball is made, its list (tar -tJf) must hold every manual
     document in share/strata/doc and every PDF file in share/strata/pdf of
     its payload.

A failure of any check is a FATAL ERROR: the status is 1, the message on the
error output names every file that is missing, empty or not a PDF file and
gives the command that makes them, and no tarball, no checksum file and no
release directory is left.  The command is 'scripts/strata-build manual'
(the install script is delivered and does not name the tool of the
developers: the tarball script gives it the command in the variable
STRATA_MANUALS_HINT).  'strata-build install' does not make the manuals
itself.  The ordinary install of a developer from a build directory
(strata-install --build-dir DIR, without --require-manuals) still only makes a
note and goes on when the PDF files are not there.

'strata-build manual' makes the manuals and their PDF files into the build
directory (manual/doc and manual/pdf below it) with manual/build.sh, target
all (the Reference Manual and the guides and cards), with the build directory
as the place of the products and the programs of the x11 build directory.  It
needs the programs built and LaTeX with the packages of the Printer
(scripts/check-tools --build --run lists what is needed).  It writes nothing
into the source tree: the targets publish and pics, which do, are not used.
It is never a part of the default build.

No PDF file is ever committed.  The PDF files are products of the build.
.gitignore has the rule *.pdf and one exception, tests/data/pics/bad.pdf (a
file of a few bytes that is not a PDF file on purpose, which a picture test
reads), and tests/pdfguard.py fails when any other file with the suffix .pdf
is tracked or when the rules are missing.  The documents of manual/doc, which
the build writes by 'publish' (never PDF files), stay committed.

The same bytes every time.  The entries are sorted by name, belong to root
(numeric owner 0), and have one time: SOURCE_DATE_EPOCH when it is set, else
the time of the commit of the source, else the time of the run.  The
compression is xz -9e.  Two runs from the same commit give the same file.

There is no signature at this time (decision of the owner, 2026-11-24).  The
SHA-256 value in the file strata-NAME.tar.xz.sha256 is the integrity check of
a release: it shows that the file that was downloaded is the file that was
published and that it is not damaged.  A reader who does not want to trust
a binary builds Strata from the source.  Nothing in the build generates a
key or signs, and the file INSTALL-USER.txt says nothing about a signature.
A signature can be added later, as a file strata-NAME.tar.xz.asc next to the
tarball, without a change of the tarball.

The instructions for the reader are INSTALL.txt: check the checksum, unpack
with tar -xJf, run 'bash strata-install'.  The install script is written
for bash, and a shell that is not bash stops at the first line that needs
bash, with a confusing message.  The script therefore starts with a test in
plain shell syntax, placed BEFORE its three set lines, because a shell that is
not bash can stop at the line with set -o pipefail (an older dash does not
know the option).  This is the one place where the script does not follow the
rule of the owner that the three set lines come right after the copyright
block; a comment in the script gives the reason.  A start with sh prints
"strata-install: run this script with bash: bash strata-install" on the
error output and ends with the status 1.

Delivery (decision of the owner, 2026-11-24).  A user downloads the tarball
from GitHub.  The files that a release publishes there are the tarball
strata-NAME.tar.xz and its checksum file strata-NAME.tar.xz.sha256, as the
files of one release of the repository.  The address of the repository and
the steps of the publication are not part of this policy: the build only
makes the two files in the build directory, and a person publishes them.
Nothing in the build or in the install script uses the network.

The test tests/installtarball.py (in the smoke list) makes the tarball from the
build directory and checks the name, the checksum file, the content, the
bytes of a second run, the install and the uninstall as an ordinary user from
the unpacked tarball, the start with sh, the text of INSTALL.txt and the
build with no supported version.  It checks that a plain 'strata-build'
leaves no tarball in the build directory and that 'strata-build install-tarball'
makes it, that every manual and PDF file is in the tarball, and that a missing,
empty or damaged PDF file, a missing document, and a build with no manual
built are each a fatal error that names the file and gives the command and
leaves nothing, with a copy of the scripts without each check failing a
check.  The tarball is made from a build directory of stand-ins (links to the
real programs and PDF files of a few bytes), so the test needs no LaTeX and
leaves the manuals of a developer alone.  It also checks that a tarball
made without the fixed time, an
INSTALL.txt that says sh, an install script without the test for bash and a
build script that makes the tarball in the default build each fail a check.


Making a release
----------------

A release is made by the tool scripts/strata-release, which takes the release
number as its argument.  It is a tool of the developers, like strata-build:
it is never shipped, and the tarball holds none of the scripts of the
developers (tests/installtarball.py checks that).

    scripts/strata-release 1.0.0 --dry-run
    scripts/strata-release 1.0.0
    scripts/strata-release 1.0.0 --rebuild

The release number is X.Y.0, with digits for X and Y: the version scheme reads
only a tag named vX.Y.0 as a release (docs/VERSIONING.txt).  The tag message
names the release, which is the first number of the version: "Strata 1.1.0
(release 1)".  The options
are --commit REV (the commit to tag, default HEAD), --jobs N and --dry-run,
which checks everything, prints the commit and the tag and changes nothing.
The build root comes from the environment and from nothing else: it is
STRATA_BUILD_ROOT, which sourcing scripts/setup sets (source scripts/setup -b
release /tmp/strata), and the tool refuses when it is not set.  The tarball
and its checksum file are made in the directory release below it, where
strata-build install makes them too.  There is no option to name the build
root or another place for the two files.

The tool makes these steps, in this order.

1. It checks, and changes nothing: the version number; the tools git, tar, xz
   and sha256sum; that the tools of the manual are there
   (scripts/check-tools --build --run: LaTeX and the packages of the Printer;
   without them a release cannot have its PDF files, and the tool refuses
   before the tag is made); that it is in a repository whose top is the project
   directory; first of all that the tag vVERSION does not exist (a tag of any
   kind, annotated or not, counts; and a remote that has it counts too); that
   the commit exists and carries no release tag already (a commit is one
   release only, because the version of a checkout is read from its release
   tag); that no tracked file is modified or staged (an untracked file does
   not count); that STRATA_BUILD_ROOT is set, that the build root is outside
   the source tree, that the scratch worktree does not exist yet and that the
   tarball of this version is not in the directory release yet (the tool never
   makes a tarball over another).  A refusal
   prints a message, ends with the status 1 and has changed nothing.  An
   existing tag is refused with "the tag vVERSION exists already: nothing was
   changed" and the advice to delete it with git tag -d if it was never
   pushed.  The tool has no option that deletes or moves a tag.
2. It makes the annotated tag vVERSION on the commit, without the option -f of
   git, so that git itself refuses a tag that appeared in between.
3. It makes a scratch worktree of the tag, detached, in
   .claude/worktrees/release-VERSION, sources scripts/setup there for a
   release build, and runs strata-build, then strata-build manual (the
   manuals and their PDF files, with LaTeX), and then strata-build install.
4. It checks the result: the version of the checkout is VERSION (so that the
   file is called strata-VERSION.tar.xz and not after a branch), the files
   strata-VERSION.tar.xz and strata-VERSION.tar.xz.sha256 exist, sha256sum -c
   passes, the tarball holds the one directory strata-VERSION and holds PDF
   files of the manuals (the tarball script has checked every one).
5. It removes the scratch worktree and prints the tag, the commit, the
   paths, the SHA-256 value, the names of the manual PDF files in the tarball
   and, as text only, the next steps.

If a step after the tag was made fails, the tool removes the tag it made, the
scratch worktree, the tarball and checksum file of this version if they were
started, and the build root if the tool made it, and says so.  It leaves a
build root that was there, and the files of other releases in it.  It never
removes a tag that it did not make.  It never pushes, never signs, never
contacts a network (except to ask a configured remote whether it has the tag
in step 1; a remote that cannot be asked is reported and the check goes on
without it), never changes the branch that is checked out, never commits and
never touches the working tree of the project.  To make a release again for
the same number, delete the tag with git tag -d vVERSION when it was not
pushed.

To make the tarball again from a tag that exists, for example on another
machine that has the tag in a clone, the option --rebuild is used:
scripts/strata-release 1.0.0 --rebuild (after source scripts/setup -b
release DIR).  The tag vVERSION must exist and must be an annotated tag of a
commit, or the tool refuses and changes nothing; --commit is an error with
it, because the tag decides the commit.  Step 1 does not ask for a free tag,
for a commit without a release tag or for an unmodified working tree (the
tag is built in the scratch worktree, not the working tree), and step 2 is
left out: no tag is made, moved or removed, whatever happens, and the tool
checks at the end that the tag is the object that it was.  Steps 3 to 5 are
the same, and the closing lines say that the tag was not changed and that
the bytes of the tarball differ from those of a release made on another
machine, because the programs and the PDF files are made by the tools of the
machine (the tar itself uses the time of the commit and sorted names): the
checksum that counts is the one of the file that was published.  A failure
removes the tarball, the scratch worktree and the build root that the tool
made, and never the tag.

The tool makes the tag and the tarball.  The release branch of section 1 of
docs/VERSIONING.txt and the publication of the files on GitHub are made by
hand.

The test tests/release.py (in the smoke list) runs the tool in a scratch
repository with small stand-ins for the build and the tarball, so that no
build is needed.  It checks the refusals, the dry run, the tag and its
message, the file names, the checksum, that nothing is pushed, the output
directory, the rollback, a tag that appears between the check and the
creation, a wrong version of the checkout, the option --rebuild (a missing
tag, a tag that is not annotated, --commit, the dry run, a real rebuild that
leaves the tag the same object, and a failed rebuild that never removes the
tag), and a dry run in the real repository.  A copy of the tool without the
check of changed files, without the rollback, without the check of the
version, with a push, without the check of the existing tag, without the
refusal of --commit with --rebuild, without the check that the tag is
annotated, that makes the tag in a rebuild or that rolls the tag back in a
rebuild each fails a check.
