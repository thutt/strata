Security of the equation images  -- DONE
-------------------------------
Note of the project owner: guard against invalid graphics images returned by
latex (a program that may be compromised), so that no buffer overflow can
happen.  The rules are in EQUATIONS.txt, section 8.
  - Done: png.c refuses a picture with more than 8000000 pixels (and a side
    above 20000), stops inflating at the exact size the header gives (a
    zlib bomb allocates at most that size), checks every filter type before
    the picture is allocated, every palette index, the palette chunk (a
    multiple of 3, 1 to 256 entries, once, before the data), every chunk
    length against what remains of the file and the CRC of every chunk,
    refuses an interlaced picture, a depth of 16 bits and any colour format
    it does not read, and does all size computations in size_t with a
    checked multiplication.  The reason of a refusal (png_error) is shown in
    the equation panel and in the list of messages of the Picture marker.
    The depth from dvipng is read as plain digits with a limit (a bad one is
    0) and is limited to the height of the picture; the cells a picture
    takes are limited to 300 in each direction.  The test is tests/pngtest.c
    (hostile pictures made at run time; it also runs under the asan build).
  - Decisions: a bad CRC is refused; data after the end chunk is ignored;
    the inflated size must be exactly right (shorter or longer is refused);
    a file is read only up to 32 MB.
  - Left: nothing for the reader.  The viewer (dviview) uses libpng for its
    images, not this reader; its own checks are a separate matter.

Markers for editing: decisions made before implementation
---------------------------------------------------------
Decisions of the project owner.  Comment, Counter, Cross-reference and Note
are implemented (the page number of a cross-reference and the pages of notes
only at print time).  A cross-reference follows its section when sections are
added, deleted, moved or sorted (MARKERS.txt).  Keycap is drawn as a box on
the X11 screen after measuring the original's graphic Preview, and a Picture
is a file that LaTeX can use, rendered like an equation; the display mode
Inline of Equation, Picture and Keycap shows the image (MARKERS.txt).

  Comment
    - A comment can be inserted anywhere in a document and edited later.
    - It has a NAME, not initials, and a TIMESTAMP of when it was created.
      (The marker has initials in field 1 today; the name replaces them and
      the timestamp needs a field of its own.  The field numbers are to be
      chosen when it is built; files of the original do not matter.)
    - Comments are printed only in DRAFT prints, never in final prints.

  Counter
    - A counter has a number format (the style of its numbers) that is
      stored with the counter and can be edited.
    - A counter marker that sets no value and no number style uses the
      default.
    - It is not the first use of the counter: its state is incremented.
    - It sets a value: the counter is set to that value before it is used.
    - Number formats wanted: arabic (1), lower and upper case roman
      (i, I) and lower and upper case letters (a, A).  The original writes
      them in a tag as \1\, \i\, \I\ and \A\ (DOC-FORMAT.txt).  Suggested
      additions, to be decided: letters that go on after z (aa, ab, as
      LaTeX does not, the choice is ours), arabic with leading zeros (01),
      and the footnote symbols (* then a dagger, a double dagger, a section
      sign, a paragraph sign and so on) for notes.  All of them map to
      LaTeX counters (\arabic, \roman, \Roman, \alph, \Alph, \fnsymbol).
    - To settle: where the format lives (the header record of the counter,
      OT<n>N and OT<n>T, or the marker, or both) and what the default and
      the first value are; MARKERS.txt has what is known of the records.

  Cross-reference
    - It prints a reference to a section.  Each cross-reference chooses how
      the reference appears: the section number, the section title, the
      section number and title, or the page number.
    - The marker has the choices Tag, Headline and Both (field XT, values
      1, 2 and 3 in DOC-FORMAT.txt); the page number is a new choice.  The
      page number is only known when the pages are made, so it belongs to
      printing (the LaTeX label and page reference).

  Keycap
    - Correct as it is described (a string such as F1, A, Ins or PrtScr in a
      rounded keycap-like box).  It is drawn on screen in X11 and printed.
      It is in both sets (editing and printing).

  Symbol
    - Removed, with Markup and Escape Codes (see REMOVAL.txt).

Documentation workflow (decided by the owner)
---------------------------------------------
  [ ] The owner's goal: in the end the .doc file is the single source of
      truth of the reference manual.  For now separate text files (the
      sources in manual/src, read by manual/mkmanual.py) are maintained
      and the single document strata-reference-manual.doc is made from
      them.  The future way in which Claude changes the documentation is
      the "save to text" model:
        1. Save the document to a text file (the whole document in one
           plain text form that keeps everything: text, attributes,
           sections, tables, markers, pictures, equations, formats).
        2. Change the text file.
        3. Read the text file and save it as a document (.doc).
        4. Prove, by a ROUND TRIP, that the text form is faithful: save
           the unchanged document to text, read the text, save as .doc,
           and the bytes (or, where the file format allows two spellings
           of the same thing, the reading of both files) must be equal.
           A change is accepted only when the round trip of the new
           document is again clean.
      - What exists today: "--text" and the export write FORMATTED plain
        text for reading (docs/ARCHITECTURE.txt: doc_load/doc_save are
        lossless, the text export is not).  The manual sources are a
        different language (the directives of mkmanual.py) that make a
        document but cannot be made back from one.  So the item needs a
        new, lossless text form of a .doc (document it in docs/, plain
        ASCII, lines of at most 80 columns where the content allows) with
        a writer (doc to text) and a reader (text to doc), built into
        the programs or as a tool next to them, and a test that makes
        the round trip of every sample document and of the reference
        manual.
      - Until it exists the workflow stays: change the sources, run
        manual/build.sh, check the round trip through the Editor
        (build.sh check).
      - When it exists: the manual sources become generated or are
        retired; the README of manual/ and the task texts for the alien
        say which model is in force.

UTF-8 instead of the code page (explore)
----------------------------------------
  [ ] Explore the idea of using UTF-8 for the text of documents instead of
      the code page that is used now (IBM CP437: one byte per character,
      docs/DOC-FORMAT.txt: "Character set is IBM CP437; text is not
      translated").  The owner's hope: this lets people of all other
      languages use the processor.  This item is an EXPLORATION: its
      result is a written study (docs/UTF8.txt), a recommendation and a
      plan, and, only if the owner agrees, the work.
      What UTF-8 alone gives, and what it does not.  UTF-8 is necessary
      for other languages but not enough.  The study must go through
      every layer and say, for each, what works now, what must change and
      what it costs (state only what was read or tried):
      - The file format (docs/DOC-FORMAT.txt): the text bytes 20-FF are
        CP437 characters.  Choices: keep the format and convert on load
        and save (loses every character outside CP437); a new format
        version with a flag in the header that says "text is UTF-8" (old
        files keep reading as CP437; a file with the flag is not readable
        by the old programs; decide how the flag is stored and how the
        Editor says which it is); or a mapping layer.  Which bytes of the
        record structure may clash with the bytes of a UTF-8 sequence
        (control bytes below 20 are structure; bytes 80-FF are text and
        UTF-8 uses them in sequences, so check that no code takes a
        byte as a unit).  Every place that treats a byte as a character:
        the text buffer, cursor movement, column counts, Delete and
        Backspace, Search and Replace, blocks and tabs, the table
        and the ruler, Compose (it makes CP437 characters today), the
        marker records, the selection and library, undo, the keyboard
        macro recorder.
      - The screen: the terminal version (how the terminal draws wide and
        combining characters; a character that takes two cells; the
        terminal lines and boxes that the Editor draws with CP437
        graphics; the defect that already exists with a character of four
        bytes typed in the terminal; the keyboard input of a locale) and
        the X11 version (fonts with the coverage; fallback fonts; input
        methods such as XIM for Chinese, Japanese, Korean and the dead
        keys of European keyboards).
      - Scripts that need more than a code point per character: right to
        left text (Arabic, Hebrew: bidirectional order, cursor movement
        in a mixed line), scripts with shaping or combining marks (Arabic,
        the Indic scripts, Thai), wide characters of Chinese, Japanese and
        Korean (two cells, no spaces between words, line breaking rules).
        Say which of these the study recommends supporting, in which
        order, and which only be shown correctly in the output.
      - The Printer: the LaTeX that src/latex.c writes uses CP437 to LaTeX
        today (put_cp437; the Error Log tells of "a character no font
        has").  With UTF-8 the choices are the utf8 input of pdflatex
        (limited by the fonts it knows), XeLaTeX or LuaLaTeX with fontspec
        and system fonts (wide coverage, a different engine than the DVI
        route that the Preview uses; check what happens to the DVI
        Preview and the Viewer, which reads DVI and shows glyphs from
        TeX fonts), babel or polyglossia for the languages, hyphenation
        patterns per language, the CJK package, and what the equations

        engines it has, and what each choice does to the pages that exist

        owner agrees).
      - The Viewer: its fonts and the way it draws glyphs of DVI files made
        by the new route.
      - Spell Check and Thesaurus: the dictionaries are per language; the
        Editor already speaks UTF-8 to hunspell and converts (docs/SPELL.txt,

        language of a block or section becomes a property (it exists in
        the format for hyphenation and the dictionary language; look).
      - Sort, case conversion, Search (case-insensitive search of letters

      - Import and export: the text export is UTF-8 already (export.c

----------------------------------------------------------

      hyphens, three hyphens, two backticks, two apostrophes, two commas,
      two less-than and two greater-than signs, "!" or "?" followed by a
      backtick), and put_legend keeps an f apart from a following f, i or
      l in a keycap legend.  Tests: tests/lxtest.c (test_escape,

      The text of the item below is the finding and the spec.
      The owner reported: the Keycap for the compound "Alt-" and "-" looks
      like a single character; compared with it "Alt-" and "+" are two
      separate characters.  Question: is the fault Strata's or LaTeX's?
      ANSWER (found with a test, kept here so that it is not found again):
      it is Strata's fault, caused by a LaTeX rule.  The writer
      (src/latex.c: emit_keycap, put_bytes) puts the legend of the keycap
      into the .tex file as the plain characters Alt--.  LaTeX turns two
      hyphens in a row in a roman or sans serif font into ONE en dash (and
      three into an em dash): that is a ligature that TeX applies to
      every text it sets.  Strata does not protect the hyphens, so
      "Alt--" prints as "Alt" followed by one dash character.  "Alt-+" is
      not changed, because a hyphen followed by a plus is no ligature.
      The test: a document with the Keycaps "Alt--", "Alt-+" and "Alt-*"
      and the plain text "-- ---" was written with the Printer's
      --tex-only (the .tex has Alt-- literally) and typeset; pdftotext of
      the PDF gives "Alt-- ... a -- b --- c" as "Alt(en dash) ... a
      (en dash) b (em dash) c" (an en dash for two hyphens, an em dash for
      three).  So the same fault is in ordinary text too: a user who types
      two hyphens in a document gets an en dash in Preview and Print.
      The old program printed two hyphens; the owner decides whether Strata
      should turn them into a dash (it does not today by design: it
      happens by accident).
      What to do:
      - Fix the writer: every hyphen of the text that Strata writes
        must reach the page as a hyphen (a minus sign of the font), one
        character each.  The usual way is to write a hyphen that is
        followed by another hyphen as "-{}" (the empty group breaks the
        ligature), or to write every hyphen of keycap legends, line
        markers and plain text that way; choose the way that does not
        change hyphenation or line breaking after a hyphen (a hyphen must
        still allow a break after it where it did).  Check the other
        ligature sequences of TeX fonts that the writer can meet in text
        and say what is done for each: "``" and "''" (quotes made from
        two backticks or two apostrophes), ",," , "<<" and ">>", "!`"
        and "?`", and the fi, fl, ff, ffi ligatures (these are fine in
        words; they are a problem only inside a keycap legend, a table
        of keys or a code listing where each character matters:
        turn them off there).  Keycap legends must never be ligatured
        or hyphenated.
      - Every other place that writes user text in the same way (the
        Error Log, the Index, the contents, headers and footers, table
        cells, equation text fallback, the failed-print banner) uses the
        same function, so the fix goes in the one function and the other

      DECIDED by the owner (2026-11-16): a backup is NOT created when the
      document is not changed.  A save of a document that has not changed
      since it was loaded or last saved (or whose new content is the same as
      the file on disk) leaves the numbered backups as they are: nothing is
      deleted, renamed or written.
      The rule, exactly: let N be the number of backups kept.  A save of
      NAME makes backup 1 from the version that is on disk before the
      save.  If the files NAME backup 1 .. N all exist: delete backup N
      (the oldest), rename backup N-1 to N, N-2 to N-1, and so on down
      to backup 1 to 2, then write the new backup 1.  If fewer than N
      exist, nothing is deleted and the existing ones are renamed up by
      one.  Backup 1 is always the newest and backup N the oldest.

        The default: 1.  The old setting "Maintain Backup File" (config key
        backup, yes or no) is replaced: a settings file that has

--------------------------------------------
  [x] DONE (see docs/LOGGING.txt): src/build_type.h, src/log.[ch], the
      defines in both Makefiles, the audit, the report file of the Viewer
      (--report) read by the Editor, the detailed message for an

      page is open.  The owner's rule, from the report that the Viewer
      printed "dviview: special '' is not supported, ignored" on the
      console after the
      Editor quit: "A release build must not log anything.  If a release
      build needs to log something, it can go to the system log, and
      probably should be a fatal error.  A debug build can log to the
      console.  In that particular case, '' is not helpful at all.  That
      particular log must print more detailed information that can be
      understood and addressed."
      - One logging facility for every program (Editor, Document Manager,
        Printer, Viewer): a small module that all of them use, so that the
        rule is kept in one place.  Release build: it writes nothing to the
        console, not even to the error output.  A condition that must be
        reported and that the user cannot see another way is sent to the
        system log (syslog), and where it means that the program cannot
        go on correctly it is a fatal error that stops the program with
        the reason (an exit code that the Editor already understands).
        Debug build: it writes to the console, with the program, the file
        and line (or the function), the severity and a message.

        command line tool (the PDF written by the Printer, the usage text
        after --help or a wrong option, the answer of an option that asks

          relation operators are not very useful, and comparing things
          that look like numbers as strings is so PHP, and we are not
          going to do that."): if BOTH sides of the expression are fully
          composed of digits (no sign, no negative numbers, no decimal
          point, no space; an empty value is undefined, not a number),
          the strings are converted to unsigned integers and the
          comparison is numeric.  So "9" is less than "10", and "09"
          equals "9" (they are the same number).  The literal of the
          marker counts: in "version < 10" the 10 is a number.
        * The size of the integer, DECIDED by the owner: unsigned 32 bit
          (0 to 4294967295).  The owner's reason: this prevents ANY edge
          case with a real 64 bit overflow.  A string of digits that
          does not fit in 32 bits (more than 4294967295) is not an
          integer: it is text (see the next bullet), never an error.
        * Everything else is text, DECIDED by the owner (rule 1 of the
          two choices the owner was given, chosen "because it doesn't
          break further down a preview or print job, and is easy to
          understand"; the other choice, an error that makes the preview
          or print fail on incompatible operands, is rejected): the
          comparison is numeric only when BOTH sides are integers (all
          digits, fitting in 32 bits).  In every other case, including
          one side an integer and the other not, BOTH sides are strings
          and are compared as text: = and # test the bytes for equality,
          and <, >, <=, >= compare the bytes in plain byte order (no
          locale; a prefix is less than the longer string).  There is
          no mixed case and no rule that makes a comparison false: the
          earlier rule that a string against a number is false is VOID.
          So with a missing variable (the string undefined): "version =
          10" is false, "version # 10" is true, "version < 10" is false
          and "version > 10" is true (as text, "undefined" comes after
          "10"); the manual says so and explains that to test for a
          missing variable one writes "version = undefined".  No
          comparison ever fails a preview or a print.
        * Tests and manual: document the whole table with examples and
          test every cell (number and number, text and text, number and
          text each way, undefined and empty values, leading zeros, the
          largest value and one more, each operator).
        * Text ordering, DECIDED by the owner: the comparison of text works
          on the ASCII ordering of the characters, NOT on UTF-8 or any
          other encoding: the order is the order of the ASCII codes, so
          a digit comes before a capital letter and a capital letter
          before a small letter ("Z" is less than "a"), and the
          comparison is case sensitive.  The manual says so.  DECIDED by
          the owner ("printable 7-bit ASCII only"): since only ASCII
          has a defined order here, a variable value and a literal
          hold only printable 7-bit ASCII characters (space to tilde,
          without the quotation marks); the panel, str and the
          program refuse any
          other byte with a message that names the rule, so no UTF-8
          sequence reaches the comparison and no result depends on how
          a character is encoded.  A value in another language is made
          ASCII outside str (a country code, a region number).
        * The aim, from the owner: the conditionals are not a full
          featured programming language, just mostly boolean conditions:
          the build type, country codes, customer region numbers; for
          mail merge and for conditional printing of a document.  A user
          who needs something complicated makes the variable values
          simple OUTSIDE str (before the variable is given to it); the
          manual says that, and that a region number made of digits is a number
          (a region number of digits is a number: 09 equals 9).  Keep it
          small: do not add operators, functions, arithmetic or
          expressions beyond "variable, operator, literal".
        * Quotes, DECIDED (the owner's suggestion, taken): a variable
          value may not hold a quotation mark (the double quote or the
          single quote) and the literal in an If marker may not either;
          the panel, str and the program refuse them with a message
          that says which rule.  So a literal needs no quoting: it is
          the text after the operator, without the spaces at its ends
          (a literal may hold spaces inside it; settle and document the
          exact form and the Error Log message of a bad expression).
          The rules for a string are then: no quote, no newline and no
          NUL (the owner said an empty value is undefined).  DECIDED by
          the owner: the maximum length of a string is 255 characters,
          for a variable name, a value and a literal; longer is
          refused with a message that names the rule; the limit is in
          the manual and tested at 255 and 256.
        * The previous question: a Merge variable (if Merge exists) still
          overrides a variable for each record: check.
      - The expression: a variable name, an operator (=, #, >, <, >=,

  - Cause, found by writing errno to a file in the child: EFAULT (errno 14),
    a bad address.  run_viewer made the list of arguments, wrote the NULL
    that ends it at index 4, and then called vars_args, which writes the
    variables of the run (--var NAME VALUE, --special NAME VALUE) from

    end: execv read the rest of the stack as pointers.  When the garbage
    happened to be a NULL (or zero) soon enough the viewer was started with
    some extra random arguments; when not, execv failed with EFAULT.  That
    is why it looked like load: str passes variables to the Editor in the
    test, so the list was unterminated in every run, and the result depended
    on what was on the stack.  The other four callers of vars_args write the
    end at the returned length and were right.

    returns.  Test: tests/fakeview.sh records its arguments (the files args

    Alt-F12 menu in some).  Some take Ctrl-<function key> (KDE: Ctrl-F1 to
    Ctrl-F4 switch desktops, which would hit Learn).  Shift-<function key>

    Editor now.  The commands of the Alt keys may therefore never reach the
    Editor in the X11 version.

    of the Alt function keys to the Shift function keys.  Against it: the
    terminals differ.  The Linux console sends Shift-F1 to Shift-F10 as the

    too much difference between window managers and between terminals to
    decide now.  If it is done later: keep the Alt keys as an undocumented
    second way; the key strip, the leaflet, the manual, the macro recorder,
    the tests and nearly every picture with the key strip change.

  - The owner: "The document being overwritten by the backup shall become the
    next backup.  Consider if there is only one backup allowed: the original
    file must be saved while the backup is renamed and then the original
    file is now named the backup: essentially a swap of the files."
  - Rule to build and to test: restoring backup k of a document D (any k):
      1. the present D becomes the new backup 1 (the other backups move up
         by one as in a save, from the oldest down, and the oldest is
         removed if the number kept N is exceeded), and
      2. the chosen backup k becomes D, and the file of backup k is the one
         that was moved into the place of D (so it is not kept twice).
    With N = 1 this is exactly a swap: D and backup 1 change names, and no
    data is lost at any moment.  If the content of backup k is the same as D,
    nothing is done and the message says so (no backup of an unchanged
    document).  The steps are done in an order in which a failure at any
    point leaves both the document and every backup intact (use rename on
    one file system, write nothing before it is safe: write the order down
    and test a failure after each step with the simulated failures of
    tests/backuptest.c).  The mode and the owner of the document are kept as
    far as possible.  Restoring when the document is open in an Editor that
    is running is the user's business: say it in the confirmation (the open
    Editor keeps the old text until it loads again).
  - Do parts 1, 2 and 3 as one job: they share the backup module, the file
    names and the panel.

The VT100 character set of the terminal programs (task 66, 2026-11-24)
  -- DONE (see VT100.txt).

    Graphics set between ESC ( 0 and ESC ( B; the setting terminal_charset
    and the Setup field take auto, utf8, vt100 and ascii.  The automatic
    choice: STRATA_ASCII and the setting; a multiplexer (UTF-8 locale: utf8,
